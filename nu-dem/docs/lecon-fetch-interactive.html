Si tu n'as jamais fait de requête HTTP en JavaScript, commence ici. Le reste du dossier ira plus vite si ces quelques notions sont claires.

fetch(), en une phrase

fetch() est une fonction qui existe déjà dans ton navigateur — tu n'as rien à installer. Elle prend une adresse en paramètre, envoie une requête vers cette adresse, et te prévient plus tard quand la réponse arrive. « Plus tard » est le mot important : entre l'envoi et la réponse, ton programme continue de tourner, il n'attend pas bras croisés.

Une URL, c'est une adresse postale

Avant d'appeler fetch(), il faut savoir où on l'envoie. Une URL se découpe en plusieurs morceaux, comme une adresse postale se découpe en rue, ville, code postal.

http://localhost:3000/acteurIndiens
Le protocole — la « langue » utilisée pour discuter avec le serveur (ici http) L'hôte et le port — quelle machine contacter, et par quelle porte d'entrée (ici, ta propre machine, port 3000) Le chemin — quelle ressource précise on demande (ici, la liste des acteurs indiens)

Dans tous les exemples de ce dossier, le serveur tourne en local — c'est pour ça que l'adresse commence par localhost. Dans un vrai projet, ce serait un nom de domaine comme https://api.monsite.com.

Pourquoi pas XMLHttpRequest ?

Avant fetch, la seule façon de faire des requêtes en JavaScript était XMLHttpRequest. Ça fonctionnait, mais il fallait écrire beaucoup de code pour des choses simples, avec une syntaxe basée sur des callbacks imbriqués, peu lisible. fetch a été conçu pour remplacer ça avec une API plus courte, basée sur les Promises — la notion qu'on découvre dans la section suivante.

GET, le réglage par défaut

Quand on écrit fetch(url) sans rien préciser d'autre, on envoie automatiquement une requête de type GET. GET veut dire « donne-moi ce qui se trouve à cette adresse, je veux juste regarder, je ne modifie rien sur le serveur ». C'est la méthode la plus courante, donc celle qui ne demande aucune option supplémentaire.

fetch("http://localhost:3000/acteurIndiens"); // équivalent à : fetch("http://localhost:3000/acteurIndiens", { method: "GET" });

Pour faire autre chose qu'un GET — créer, modifier, supprimer — il faudra ajouter un deuxième argument à fetch : un objet d'options. On verra ça en détail dans la section « Méthodes ».

Pièce 1

Une Promise, c'est un ticket de commande

fetch() ne te donne jamais directement les données. Il te donne une Promise — un objet qui représente « un résultat qui n'est pas encore là, mais qui arrivera ».

Les trois états d'une Promise

Une Promise existe toujours dans un de ces trois états : en attente (pending) — la réponse n'est pas encore arrivée ; résolue (fulfilled) — tout s'est bien passé, le résultat est disponible ; rejetée (rejected) — quelque chose a empêché d'obtenir le résultat.

Imagine que tu commandes un café. Le serveur ne te le donne pas tout de suite : il te tend un ticket numéroté et te dit « je t'appelle quand c'est prêt ». Ce ticket, c'est ta Promise. Pendant que tu attends, tu peux faire autre chose — c'est exactement ce que fait ton code JavaScript pendant qu'il attend la réponse du serveur. Clique sur le bouton pour commander, et regarde le ticket changer d'état.

en attente = pending résolue = fulfilled rejetée = rejected

Deux façons d'attendre le résultat

Une fois qu'on a une Promise entre les mains, il existe deux écritures différentes pour réagir quand elle se termine. Elles font exactement la même chose en coulisses — ce n'est qu'une question de lisibilité.

On dit au serveur « appelle-moi quand c'est prêt ». Chaque .then() reçoit le résultat de l'étape précédente et le transmet à la suite — comme une chaîne d'instructions.

fetch("http://localhost:3000/acteurIndiens") .then(reponse => reponse.json()) // étape 1 : on ouvre l'enveloppe .then(donnees => { // étape 2 : on utilise les données console.log(donnees); }) .catch(erreur => { // si une étape échoue techniquement console.log(erreur); }) .finally(() => { // dans tous les cas, à la fin console.log("Terminé, quoi qu'il arrive"); });

C'est comme rester debout au comptoir à attendre ton café avant de continuer. Le mot-clé await met en pause la fonction — sans bloquer le reste de la page — jusqu'à ce que la Promise se termine, puis te donne directement la valeur, sans callback imbriqué.

async function recupererDonnees() { // "async" autorise le mot await à l'intérieur try { const reponse = await fetch("http://localhost:3000/acteurIndiens"); const donnees = await reponse.json(); console.log(donnees); } catch (erreur) { // si une étape échoue techniquement console.log(erreur); } } recupererDonnees(); // on doit appeler la fonction pour la lancer
À retenir — les deux écritures sont interchangeables. async/await est en réalité réécrit par le moteur JavaScript en quelque chose d'équivalent à des .then() enchaînés ; c'est juste plus agréable à lire une fois qu'on a plusieurs étapes à la suite.
Pièce 2

La réponse arrive en deux temps, comme une lettre

Quand la Promise se résout, elle ne donne pas directement les données — elle donne un objet Response, qui représente toute la réponse HTTP : le statut, les en-têtes, et un corps qu'il faut encore lire.

L'enveloppe, puis la lettre

reponse est l'enveloppe : on peut déjà voir le statut (200, 404, 500…) et les en-têtes écrits dessus, mais le contenu à l'intérieur n'a pas encore été lu. reponse.json(), c'est le moment où on ouvre l'enveloppe pour lire ce qu'elle contient et le transformer en objet JavaScript utilisable. Cette étape est elle aussi asynchrone — donc avec un second await — car parser le texte brut envoyé par le serveur prend un peu de temps, surtout si la réponse est volumineuse.

200 OK
[{ id: "1", nom: "..." }, { id: "2", nom: "..." }]

Étape 1 — clique sur l'enveloppe pour voir le statut

const reponse = await fetch(url); console.log(reponse.status); // l'enveloppe const donnees = await reponse.json(); // on l'ouvre

Que peut-on lire dans l'enveloppe ?

L'objet reponse contient plusieurs informations utiles, accessibles avant même d'ouvrir le contenu :

PropriétéÀ quoi ça sert
reponse.statusLe code HTTP exact (200, 404, 500…)
reponse.oktrue si le statut est entre 200 et 299
reponse.statusTextLe libellé du statut ("OK", "Not Found"…)
reponse.headersLes en-têtes envoyés par le serveur

Plusieurs façons d'ouvrir l'enveloppe

Selon ce que le serveur envoie, on ne lit pas toujours le contenu de la même façon :

reponse.json()
Pour transformer du texte JSON en objet ou tableau JavaScript — le cas le plus fréquent.
reponse.text()
Pour récupérer du texte brut, par exemple du HTML.
reponse.blob()
Pour des fichiers binaires : image, vidéo, PDF.
reponse.formData()
Pour des données envoyées au format formulaire.
Piège à connaître — on ne peut lire le contenu d'une réponse qu'une seule fois. Si tu appelles reponse.json() deux fois sur le même objet, la deuxième tentative échoue.
Pièce 3

Chaque méthode HTTP touche la fiche différemment

Imagine une fiche d'acteur dans un classeur. Chaque méthode HTTP correspond à une action différente sur cette fiche : regarder, ajouter, remplacer, corriger, ou arracher.

GET
Lire une fiche. Ne change rien. Aucune option à ajouter, c'est le réglage par défaut.
POST
Ajouter une nouvelle fiche au classeur. On envoie la fiche complète dans le body.
PUT
Remplacer entièrement une fiche existante. Tout champ absent du nouvel objet disparaît.
PATCH
Corriger juste une ou plusieurs lignes, sans toucher au reste de la fiche.
DELETE
Arracher la fiche du classeur. Pas besoin d'envoyer de données, l'adresse suffit.

Essaie chaque bouton sur la fiche ci-dessous pour voir l'effet exact de chaque méthode, et regarde le code correspondant à droite.

GET → pas d'options nécessaires

Pourquoi headers et JSON.stringify ?

Pour POST, PUT et PATCH, deux éléments reviennent systématiquement dans le code, et il faut comprendre pourquoi ils sont là.

headers: { "Content-Type": "application/json" }
C'est une étiquette qu'on colle sur l'enveloppe avant de l'envoyer, pour dire au serveur « ce que je t'envoie est écrit en JSON », afin qu'il sache comment le lire.
JSON.stringify(objet)
HTTP ne sait transporter que du texte, jamais un objet JavaScript directement. Cette fonction convertit l'objet en une chaîne de texte au format JSON avant l'envoi.

PUT contre PATCH : la nuance qui piège tout le monde

C'est la confusion la plus fréquente. Avec PUT, on envoie une fiche complète qui remplace entièrement l'ancienne — si on oublie un champ dans le nouvel objet, ce champ disparaît purement et simplement, comme tu as pu le voir en testant le bouton PUT plus haut. Avec PATCH, on n'envoie que les champs qu'on veut modifier ; tous les autres champs de la fiche restent intacts, intouchés.

Pièce 4

try/catch n'attrape pas tout

C'est sans doute le piège le plus fréquent chez les débutants : on imagine que try/catch attrape toute erreur, y compris les erreurs HTTP comme 404 ou 500. C'est faux.

Deux familles d'échecs très différentes

fetch() ne rejette sa Promise — donc ne déclenche le catch — que si la requête échoue techniquement : pas de réseau, serveur introuvable, requête bloquée par CORS. Mais si le serveur répond bien, même avec un code d'erreur comme 404 (« ressource introuvable »), fetch considère que la communication a réussi : aucune exception n'est levée, le catch reste silencieux. Compare les deux scénarios ci-dessous.

try { await fetch(url) }
catch (erreur) → TypeError
reponse.status → à vérifier soi-même

La bonne pratique à retenir

Puisque catch ne couvre pas les erreurs HTTP, il faut vérifier soi-même reponse.ok (ou reponse.status) juste après le fetch, et déclencher une erreur manuellement si besoin :

try { const reponse = await fetch("http://localhost:3000/acteurIndiens/999"); if (!reponse.ok) { throw new Error(`Erreur HTTP : ${reponse.status}`); // on force le passage par catch } const donnees = await reponse.json(); console.log(donnees); } catch (erreur) { console.log("Quelque chose s'est mal passé :", erreur.message); }

Petit lexique, pour relire plus tard

Promise
Un objet qui représente un résultat pas encore disponible, mais qui arrivera (ou échouera) plus tard.
async
Mot-clé placé devant une fonction pour autoriser l'utilisation d'await à l'intérieur.
await
Met en pause une fonction async jusqu'à ce qu'une Promise se termine, sans bloquer le reste du programme.
JSON
Un format de texte standard pour représenter des données structurées, lisible à la fois par les humains et les programmes.
Header (en-tête)
Une métadonnée jointe à une requête ou une réponse HTTP, par exemple le type de contenu envoyé.
Statut HTTP
Un code à trois chiffres qui résume le résultat d'une requête : 200 (succès), 404 (introuvable), 500 (erreur serveur)...
Body
Le contenu transporté par une requête ou une réponse — les données elles-mêmes, au-delà des en-têtes.
Endpoint
Une adresse précise exposée par une API, correspondant à une ressource ou une action (ex : /acteurIndiens/3).
